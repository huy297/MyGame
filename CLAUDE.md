# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A top-down survival game in C++ using SDL2 (with SDL2_image, SDL2_ttf, SDL2_mixer). The player moves with WASD, switches weapons with `1`/`2`/`3` (sword/gun/grenade), and attacks with `Space`. Bots spawn continuously; killing them raises the score. Picking up items (ammo/HP/grenades) refills resources. The game ends when HP reaches 0.

## Build

The build is CMake-based (`CMakeLists.txt`, C++17) and links **system SDL2** (SDL2, SDL2_image, SDL2_ttf, SDL2_mixer) found via `find_package`. Contributors install SDL2 themselves (macOS: `brew install sdl2 sdl2_image sdl2_ttf sdl2_mixer`; Debian/Ubuntu: the `libsdl2*-dev` packages).

```
cmake -B build
cmake --build build
./build/MyGame        # assets (Img/, MyMap/, sound/) are copied next to the binary post-build
```

Source lives under `src/`, grouped by architectural area (see below), and is listed explicitly in `CMakeLists.txt`. `target_include_directories` points at `src/`, so every `#include` is written path-qualified from there (e.g. `#include "core/Defs.h"`, `#include "entities/Entity.h"`) regardless of which file is including it — this avoids ambiguity and keeps includes meaningful when grepped in isolation. There is no test runner. A POST_BUILD step mirrors the three asset dirs (`Img/`, `MyMap/`, `sound/`, still at the repo root) next to the binary, so the game runs from the build tree; if you run the binary directly, its working directory must contain those three.

```
src/
├── Main.cpp        # entry point / state-machine loop
├── core/            Defs.h, Game.h/.cpp, World.h/.cpp
├── entities/        Entity.h/.cpp, Character.h/.cpp, Weapons.h/.cpp, Items.h/.cpp
├── graphics/        Graphics.h/.cpp
└── map/             Map.h/.cpp, Logic.h, Algo.h/.cpp
```

## Asset paths

Asset load paths in code are **case-sensitive and must exactly match the on-disk (Git-recorded) filenames** — the directories are `Img/`, `MyMap/`, `sound/` and several files are capitalized (`Simple.png`, `Sword.png`, `Grenade.png`, `Play.png`, `Exit.png`, `Explosion.png`) while others are lowercase (`gren.png`, `bullet.png`). These were reconciled to build on case-sensitive filesystems (Linux); when adding assets, match the exact casing. Building with `-Wall` surfaces `-Wnonportable-include-path` if an `#include` casing drifts, too.

## Architecture

### Game loop & state machine (`src/Main.cpp`, `src/core/Game.h/.cpp`)
`main()` runs an outer loop dispatching on a global `GameState` (`Menu` / `Playing` / `EndGame`, defined in `Game.h`). Each state has its own inner loop that calls the matching `Game` methods and polls `game->changeState()` to detect transitions (menu button clicks, HP≤0, replay). `Game::reset()` is called on returning to play from `EndGame`. `game` is a stack-local `Game` in `main()` (not heap-allocated) so its destructor runs on the way out.

Each inner loop paces itself to ~50ms/20fps via `paceFrame()`, which captures `SDL_GetTicks()` at the top of the loop and sleeps only the remainder of the 50ms budget (`FRAME_MS`) after the frame's work is done — a flat `SDL_Delay(50)` (the old behavior) doesn't account for time already spent in that frame's update/render, so the true period becomes `work_time + 50ms` and drifts under load instead of staying steady.

`Game` owns the SDL window and the **static** `SDL_Renderer* Game::renderer` shared by all rendering code, plus a `unique_ptr<World>` (the playthrough state) and a `unique_ptr<Map>` (loaded once, persists across `reset()`). `Game::init()` sets up SDL/Mix/TTF/IMG and loads fonts/UI textures.

**Quitting is a flag, not `exit()`.** All four quit points (`SDL_QUIT` in `handleEvents()`/`handleMouse()`, the "Exit" button in `changeState()` from both `Menu` and `EndGame`) set `Game::quitRequested = true` instead of calling `exit()`. Every loop condition in `Main.cpp` checks it, so control unwinds naturally out of `main()` and `~Game()` actually runs — `exit()` would skip it entirely. `~Game()` tears down in reverse-acquisition order: `world`/`gameMap` reset, the 4 `loadText`-created UI textures (`score`/`hp`/`ammo`/`grenadeTexture` — not cache-managed) explicitly `SDL_DestroyTexture`'d, `Graphics::clearCache()` (destroys every `loadTexture()`-cached texture — this used to be dead code, never called), font closed, renderer/window destroyed, then `Mix_CloseAudio`/`TTF_Quit`/`IMG_Quit`/`SDL_Quit`. If you add a new acquired resource (texture, sound, subsystem), add its teardown here in the matching reverse position — there's no other cleanup path. Verified leak-free with macOS's `leaks --atExit` after a full init→play→quit cycle (0 leaks) since neither ASan nor Valgrind's leak detection runs on macOS the same way.

`Game::updateEvents()` only regenerates a HUD stat's texture (score/hp/ammo/grenade — each a `TTF_RenderText_Solid` + `SDL_CreateTextureFromSurface` + `SDL_DestroyTexture` on the old one) when that stat's value actually changed since last frame, tracked via file-local `lastScore`/`lastHp`/`lastMagazine`/`lastNumGren` (reset to `-1` in `init()`/`reset()` so the first frame always populates). Regenerating unconditionally every frame — the old behavior — meant paying that cost 4x/frame (~20x/sec) even though these stats are static most frames; measured with instrumentation: 800 calls over 200 frames naively vs. 4 actual calls with the dirty-check (in a run where nothing changed after the first frame).

While verifying this, `leaks`/ASan surfaced a real pre-existing bug (not introduced by the cleanup work, just newly reachable after the `Algo.h` `N` bounds fix): `Logic::canMove`/`canGetThrough` and `Map::blockedSize` computed tile indices from pixel coordinates with no bounds check against the 80×80 `Map::isWalkable`/`isBlocked`/`numBlocked` grids, so a query at/near the true map edge (pixel ~3840) could read one past the array. Fixed by bounds-checking in `canMove`/`canGetThrough` (out-of-range → `false`, i.e. can't move/see off the map) and clamping corners in `blockedSize` (query rectangle restricted to the on-map portion). Worth remembering if you touch tile-coordinate math anywhere else in `Logic.h`/`Map.h`: always bounds-check before indexing the static grids, they don't do it themselves.

### Entities (`src/entities/`: `Entity.h/.cpp`, `Weapons.h/.cpp`, `Character.h/.cpp`, `Items.h/.cpp`)
`Entity` is the base movable object (position, velocity, direction, hp, ammo). `Character` composes an `Entity` player with a `Gun`, `Sword`, and `Grenade`; `Bot` extends `Character` with AI (`updateInput`). Weapons derive from `Weapon`; effects (`SwordSlash`, `Explosion`) derive from `WeaponEffect`. `Death` and `Item` live in `Items.h/.cpp`. All rect/texture ownership is `std::unique_ptr` (no manual `new`/`delete`); methods that need to check collisions or spawn other entities take a `World&` parameter.

### The `World` (`src/core/World.h`, `src/core/World.cpp`)
`World` owns everything that resets between playthroughs: the player `Character`, and owning containers for the transient entity lists — `bots`, `bullets`, `deaths`, `items` (each `std::list<std::unique_ptr<T>>`). This replaces what used to be `static std::list<T*>` members scattered across `Bot`/`Gun`/`Death`/`Item` and defined as loose globals in `Game.cpp`. `World::update()` drives one frame: player update, bot spawn/update/reap, item spawn/update, bullet update, death update — **in that specific order**, which matters (see the comment in `World::update()`): the player moves against the collidable-entity snapshot left over from the *previous* frame, while bots/items/bullets see the current frame's freshly rebuilt list. `Game::reset()` just replaces the whole `World` with a fresh one.

`World` also exposes the collision/spawn queries entities need: `isPathClear`, `bulletCanAdvance`, `grenadeCanAdvance`, `damageAreaAroundExplosion`, `spawnDeath`, and `collidables()` (the per-frame snapshot used for hit-testing).

Movement/hit collision checks used to be O(live bot count) per bot per frame (every bot's move check scanned the whole collidable list), so `World::spawnBots()` caps concurrent bots at `MAX_BOTS` (`Defs.h`) — without it, a long playthrough accumulates bots forever and the per-frame cost grows unbounded (measured: unbounded growth from ~4ms to 11ms+ and climbing over a few hundred frames with no cap; flat 1-4ms indefinitely with it).

That O(n²) collision scan was replaced with a uniform spatial grid: `grid_[MAPSIZE][MAPSIZE]` (a `World` member, one bucket per map tile — same tile size as `Logic::canMove`/`Map::isWalkable`) is rebuilt each frame in `rebuildCollidables()` alongside `collidables_`, clearing only the specific cells touched last frame (tracked in `touchedCells_`, mirroring the `visitedGen` lazy-reset idea in `Algo.cpp` — not a full `MAPSIZE²`-cell reset every frame). `isPathClear`/`bulletCanAdvance`/`grenadeCanAdvance` now call `nearbyEntities(rect)`, which only scans the 3x3 neighborhood of buckets around the query rect's own tile, instead of iterating all of `collidables_`. This is safe because every rect type that goes through these three functions is at most one tile in size (player/bots 48x48, bullets 16x16, grenades-in-flight ≤48x32) — a true overlap between two such rects can only occur when they're in adjacent tiles, so the 3x3 neighborhood always catches it. (The much larger 128x128 explosion-damage rect is unrelated: `damageAreaAroundExplosion` iterates `bots` directly, not through `nearbyEntities`.) Measured at `MAX_BOTS`=60 with the player away from the bot cluster: `nearbyEntities()` returned as few as 1 candidate vs. 61 in `collidables_` — the win scales with how spread out entities are, which matters most as bot/entity counts grow past today's cap (the original motivation for revisiting this). If you touch the query functions, keep going through `nearbyEntities()` rather than `collidables_` directly, and if you add a new rect type that can be larger than one tile, widen the neighborhood radius accordingly (verify against real rect sizes — don't assume 3x3 is always enough).

Separately, `spawnBots()`/`spawnItems()` pick a random spawn position validated only against tile walkability (`Logic::canMove`), not against other entities already there — two bots can spawn overlapping each other. This is a pre-existing gap (confirmed via a control test: the same brute-force overlap count showed up whether collision queries went through `collidables_` directly or through the new spatial grid), not something introduced by the grid change, and out of scope here.

`updateBots()` also has a use-after-free trap worth knowing about if you touch it: bots can kill each other (sword/bullet splash isn't restricted to hitting only the player), so **every bot must get its `updateInput()` turn before any dead bot is erased** from the list — erasing frees that bot's `Entity`, and `collidables_` holds raw pointers into it. `rebuildCollidables()` also needs to be called again after the reap pass (not just before the update pass), because `updateItems()`/`updateBullets()` run afterward in the same frame and read the same list.

### Rendering & camera (`src/graphics/Graphics.h`, `src/graphics/Graphics.cpp`)
`Graphics` is an all-static utility class. World objects are drawn in world coordinates; a camera offset (file-local to `Graphics.cpp`) is subtracted inside `blitRect()` to convert to screen space. The camera follows the player: `Game::updateEvents()` sets `offset = playerPos - startPos`, and `Graphics::updateOffset()` computes the per-frame delta used to scroll the map's `srcRect`. `drawCharacter()` handles one `Character` (player or bot); `drawAll(const World&)` iterates `World`'s bots/deaths/items/bullets. Text and sound helpers (`loadFont`, `loadText`, `updateText`, `loadSound`, `play`) are inline in `Graphics.h`.

`drawMap()` scrolls the map's `srcRect` by the per-frame camera delta with nothing else constraining it, so walking far enough in any direction pushes `srcRect` negative or past the far edge of the map texture; SDL then samples out-of-bounds texture data, which looks like the map suddenly zooming/losing aspect ratio rather than scrolling. `drawMap()` clamps `srcRect->x`/`y` against the actual texture bounds (queried via `SDL_QueryTexture`, since the map texture is the source of truth for size) every frame — don't remove this without another way to bound the camera. Relatedly, `Game::renderEndGame()` (the death-screen loop) has to call `Graphics::updateOffset()` itself before `drawMap()`; `Game::updateEvents()` (and with it the offset computation) stops running once the player dies, so without that call the last pre-death delta would keep getting reapplied every frame, scrolling the death-screen background forever instead of freezing it.

### Map & collision (`src/map/`: `Map.h/.cpp`, `Logic.h`, `Algo.h/.cpp`; `src/core/Defs.h`)
The map is `MAPSIZE`×`MAPSIZE` (80×80) tiles of `SPRITE_X`×`SPRITE_Y` (48px). `Map::LoadMap()` reads four layer files `MyMap/mymap0..3.txt` by redirecting `stdin` with `freopen` and parsing comma-separated tile data in `ProcessData()`; layer index determines walkable/blocked semantics. Static grids `Map::isWalkable` and `Map::isBlocked` back movement checks.

Collision and line-of-sight live in `Logic.h` (static-only `Logic` class): `canMove`, `canGetThrough`, `canShoot`, `canSlash`, plus `intersect`/`randomInt`. Fast rectangle "is anything blocking" queries use a **2D prefix-sum** over blocked tiles: `Map::numBlocked` is summed into prefix sums at the end of `LoadMap()`, and `Map::blockedSize(x1,y1,x2,y2)` answers a rectangle query in O(1) — this is what `canShoot` uses to test whether walls interrupt a shot.

Bot pathfinding is a breadth-first flood-fill (`Algo.h/.cpp`, `computeBotDirections()`) run once per frame from the target player's position; `traceDirection(gx, gy)` gives the direction a bot standing at that grid cell should move in to head toward the target, or `-1` if that cell hasn't been reached yet (out of bounds, disconnected, or — notably — the very first frame or two after the player spawns, since the spawn point `SCREEN_HEIGHT/2+50, SCREEN_WIDTH/2+50` sits inside the map's forced-unwalkable border and the flood can't originate from an unwalkable tile). Bots share this single-source flood, so they all currently path toward one designated target rather than each having independent targets.

This used to be a *weighted* Dijkstra (`std::priority_queue`, random edge weights, full `std::shuffle` per node, and a full `O(N²)` grid reset every call) — measured at **~94ms per call** on a fully-open map region (it touched ~120k grid cells every single frame, more than the entire 50ms frame budget). Since the weights were random anyway (not modeling any real cost), it was rewritten as unweighted BFS (`std::queue`, an O(1) 24-entry permutation-table lookup instead of `std::shuffle`, and generational lazy-reset instead of memset — see `visitedGen`/`currentGen` in `Algo.cpp`) with no change to the walls/reachability logic. Measured after: **~16ms per call**, ~5.7x faster, same reachable set. If you touch `computeBotDirections()`, preserve two things: (1) cells not visited this generation must read back as `-1` through `traceDirection()`, not a stale direction from a previous call — that's what `visitedGen` enforces; (2) `Bot::updateInput()` explicitly treats `dir == -1` as "hold position" before doing any bitwise direction check, because `-1` has every direction bit set and will otherwise silently corrupt `currentDir`/facing.

Even at ~16ms, recomputing the full flood every single frame is wasted work, since the player (the flood's target) moves only a few pixels between frames. `World::updateBots()` throttles this via a `botPathTick_` counter: `computeBotDirections()` only runs when `botPathTick_ % 3 == 0`, while `traceDirection()` lookups (already O(1)) keep running every frame off whatever flood is currently cached — verified via instrumentation that the call count tracks `~totalFrames/3` as expected. This is a deliberate tradeoff: a bot's path target can lag up to ~2 frames (~100ms) behind the player's actual position. Acceptable since bots move far slower than a tile per 100ms; if bot responsiveness ever needs to be tighter (e.g. for faster enemies), lower or remove this throttle rather than reintroducing a full recompute elsewhere.

`Defs.h` holds all tunable constants (screen/sprite sizes, `MAPSIZE`, `MAX_BOTS`) and the **direction bitmask** (`Up=1, Down=2, Left=4, Right=8`, with diagonals as combined values like `RightAndUp=9`). Direction values throughout the code are these bit flags, not enum ordinals.

## Style
A `.clang-format` at the repo root (4-space indent, Allman braces, no column limit) defines the formatting convention. Run `clang-format -i` over changed files (or `clang-format -i src/**/*.h src/**/*.cpp` for everything) before committing — it only touches whitespace, never semantics, so it's safe to run freely.
